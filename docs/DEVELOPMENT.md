# Developing HostKeeper

## Requirements

- macOS 14 or later
- Xcode 16 or later (includes Swift 6)
- Optional: the [GitHub CLI](https://cli.github.com) (`brew install gh`) for releases

## Project layout

| Path | What's there |
|---|---|
| `Sources/SSHConfigKit/` | Reads and writes ssh config files. No UI, fully unit-tested. |
| `Sources/HostKeeper/` | The SwiftUI app: windows, key management, help. |
| `Tests/HostKeeperTests/` | Tests for SSHConfigKit. |
| `Resources/AppIcon.icns` | App icon, generated by `scripts/make-icon.swift`. |
| `build-app.sh` | Builds the release `.app` (with Sparkle inside), `.dmg` and `.zip`. |
| `scripts/release_files.py` | Writes the update feed (`appcast.xml`) and Homebrew cask for a release. |
| `Casks/hostkeeper.rb` | The Homebrew cask. The release workflow updates it; don't edit it by hand. |
| `.github/workflows/` | CI (tests and changelog check) and release builds. |

## Practice mode: your real config is safe

**Debug builds never touch your real `~/.ssh`.** When you run from Xcode (⌘R) or with `swift run`, HostKeeper uses a practice folder:

```
~/Library/Application Support/HostKeeper-Dev/ssh/
```

It's created with a sample config the first time, and a yellow bar at the bottom of the window shows you're in practice mode. Keys you generate or delete there are practice keys too. To start over, delete that folder.

Release builds (`./build-app.sh`, and the download on GitHub) use the real `~/.ssh`.

To point any build at another folder, set `HOSTKEEPER_SSH_DIR`, for example in Xcode under **Product → Scheme → Edit Scheme → Run → Arguments → Environment Variables**.

## Running it

**In Xcode:**

```bash
open Package.swift
```

Pick the **HostKeeper** scheme and **My Mac**, then press ⌘R to run or ⌘U to run the tests.

**From Terminal:**

```bash
swift run HostKeeper
```

```bash
swift test
```

## Day-to-day workflow

1. Create a branch for each change:

   ```bash
   git switch -c add-port-forwarding-ui
   ```

2. Make changes, run the app in practice mode, and run `swift test`.
3. **Write it down.** Add a line under `## Unreleased` in `CHANGELOG.md`, written for people who use the app. If you added or changed a feature, update `README.md` and the Help window (`HelpView.swift`) too.
4. Commit and push, then open a pull request:

   ```bash
   git push -u origin HEAD
   ```

   ```bash
   gh pr create --fill
   ```

5. GitHub runs the tests on the pull request, and fails it if app code changed without a `CHANGELOG.md` entry. For changes users won't notice (refactoring, CI tweaks), add the **skip-changelog** label instead. The pull request description includes a checklist as a reminder. Merge when everything passes.

`main` should always be in a working state, because releases are built from it.

## Making a release

1. In `Sources/HostKeeper/Version.swift`, update `version` (`1.4.1` for fixes, `1.5.0` for new features) and **always increase `build` by one**. Sparkle compares build numbers to decide what's newer.
2. In `CHANGELOG.md`, rename `## Unreleased` to the new version (for example `## 1.5.0`) and add a fresh empty `## Unreleased` above it.
3. Check the README still describes the app accurately.
4. Commit, tag and push:

   ```bash
   git commit -am "Release 1.5.0"
   ```

   ```bash
   git tag v1.5.0
   ```

   ```bash
   git push origin main --tags
   ```

The **Release** workflow then, in about five minutes:

1. Checks the tag matches `Version.swift` and that `CHANGELOG.md` has notes for that version.
2. Runs the tests and builds the app, DMG and ZIP.
3. Signs the ZIP with the update key and writes `appcast.xml`, using the changelog entry as the "what's new" notes.
4. Publishes a GitHub Release with the DMG, ZIP and `appcast.xml`.
5. Commits the updated `Casks/hostkeeper.rb` to `main`, so `brew upgrade` sees it.

Installed copies find the update through `releases/latest/download/appcast.xml`, within a day, or right away with **Check for Updates…**. Watch the workflow under the repository's **Actions** tab.

To build the downloads locally instead, run `./build-app.sh`; they're written to `build/`.

## How updates work

HostKeeper uses [Sparkle](https://sparkle-project.org). Each release's `appcast.xml` describes the newest version and includes a signature of its ZIP. The app downloads the feed from the latest GitHub release, compares build numbers, shows the changelog notes, and installs the ZIP only if its signature matches the public key built into the app (`SPARKLE_PUBLIC_KEY` in `build-app.sh`).

Development builds (Xcode, `swift run`) don't check for updates.

### The update signing key: back it up

The private key is stored in two places: your Mac's **login Keychain** (as "Private key for signing Sparkle updates") and the **SPARKLE_PRIVATE_KEY** secret on GitHub, which can't be read back. **If you lose it, installed copies can never be updated again**; everyone would have to download a new version by hand.

Back it up now to a password manager or another safe place:

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys -x ~/Desktop/hostkeeper-sparkle-key.txt
```

Store that file's contents somewhere safe, then delete the file. Never commit it or share it.

If you get a new Mac, import it with `generate_keys -f <file>`.

## Homebrew

The repository is its own Homebrew tap, so people install with:

```bash
brew tap ericrwilson/hostkeeper https://github.com/EricRWilson/HostKeeper
```

```bash
brew install --cask hostkeeper
```

The release workflow updates `Casks/hostkeeper.rb` with each release's version and checksum. The cask has `auto_updates true`, so Homebrew knows Sparkle can update the app too.

## Changing the icon

Edit the drawing code in `scripts/make-icon.swift`, then regenerate:

```bash
swift scripts/make-icon.swift
```

This rewrites `Resources/AppIcon.icns` and `docs/logo.png`.

## Code signing

Downloads are ad-hoc signed, so people approve the app once in **System Settings → Privacy & Security** (the README explains how). To remove that step you'd need a paid Apple Developer ID ($99/year) to sign and notarize the app. The release workflow would then gain a signing step, with the certificate stored as a GitHub secret.
